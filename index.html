PART I

The Substrate

FIG·01

From prompt to token to inference

The full round trip of one generated token: text is tokenized to integer IDs, embedded, pushed through the transformer stack, scored into logits, sampled — then the chosen token is appended and the whole thing runs again. An "agent thinking" is this loop, thousands of times.

SUBSTRATE

Design notes

  • Tokens are the only currency. The model never sees words, JSON, or "instructions" — just integer IDs. Every prompt-engineering trick is really token-sequence engineering.
  • The KV cache is why long contexts are viable: attention keys/values for past tokens are computed once, then reused every subsequent step.
  • Sampling parameters live outside the model — same logits, different temperature, different agent behavior. Treat them as config under version control.

What breaks

  • Tokenizer surprises: whitespace, numbers, and rare strings split unpredictably — string-length budgeting drifts from token-length reality.
  • KV cache memory grows linearly with sequence length × layers — long agent sessions get evicted or repriced, not "slow".
  • Greedy decoding isn't determinism: batching, kernels, and floating-point order still introduce run-to-run variance. Evals must assume it.
FIG·02

The inference serving path

What sits between your messages.create() and the GPU: gateways, routing, continuous batching, and the prefill/decode split. Latency and cost behavior of every agent is decided in this pipeline.

SUBSTRATE

Design notes

  • Prefill and decode are different workloads: prefill chews the whole prompt in parallel (compute-bound); decode emits one token per step (memory-bandwidth-bound). Time-to-first-token and tokens/sec are set by different hardware limits.
  • Continuous batching lets new requests join at every decode step — throughput without head-of-line blocking. It's why your p50 and p99 diverge under load.
  • Prompt caching is an architecture decision, not a discount: stable prefixes (system prompt, tool schemas) should come first so repeated calls skip prefill.

What breaks

  • Agents multiply this path: a 20-step run is 20 serving round-trips. Per-request overhead that's invisible in a chatbot dominates in an agent.
  • One byte changed early in the prompt invalidates the cached prefix — a "harmless" dynamic timestamp in the system prompt can double your bill.
  • Rate limits hit token throughput, not request count. Fan-out (multi-agent) designs need budgets per branch or they starve each other.
FIG·03

Context window assembly

"Context engineering" is a build step. Six competing sources get prioritized, budgeted, truncated, and ordered into one flat token array — because that's all the model ever receives.

SUBSTRATE

Design notes

  • Budget explicitly. Give every source a token allowance and an eviction policy (drop, truncate, summarize). Implicit budgets fail silently at the worst time.
  • Order for the cache: stable content (system prompt, tool schemas) first, volatile content last — the prefix stays cacheable across every loop iteration.
  • Reserve headroom for the response. An assembler that fills 100% of the window starves the model's output.

What breaks

  • Context rot: stale tool results and dead-end reasoning accumulate in history and steer later steps. Compaction is a correctness feature, not a cost feature.
  • Retrieved chunks and memory compete for the same budget — without priorities, RAG floods out the user's actual question.
  • "Lost in the middle": models attend best to the start and end of the window. Where you place instructions changes whether they're followed.
PART II

The Agent Core

FIG·04

The agent loop

An agent is a while-loop around inference: the model reads context, emits either an answer or a tool call, the runtime executes, and the observation is appended back into context. Everything else in this atlas hangs off this cycle.

AGENT CORE

Design notes

  • The model proposes, the runtime disposes. Steps 4–5 are ordinary deterministic code — this is where permissions, sandboxing, retries, and logging live, because it's the only place they can live.
  • The loop is stateless per step: nothing persists between iterations except what's written into context. Design the observation format as carefully as the prompt.
  • Always bound the loop (turns, tokens, wall-clock). "The model will stop eventually" is not a termination condition.

What breaks

  • Doom loops: same tool, same args, same failure, forever. Detect repeated (tool, args) signatures and break the cycle with an error or escalation.
  • Growing context shifts behavior: step 30 sees a very different window than step 2. Long-horizon evals must measure late-loop quality, not just first-turn quality.
  • Silent tool failures that return empty-but-valid results teach the model false beliefs it acts on three steps later.
FIG·05

Anatomy of a tool call

Sequence view of a single tool invocation. The model only ever emits text; seven runtime steps turn that text into a validated, permissioned, executed side-effect — and back into tokens.

AGENT CORE

Design notes

  • Schema design is prompt design: the tool's name, description, and parameter names are read by the model as instructions. Vague schemas produce vague calls.
  • Validate before permission-check, and feed validation errors back verbatim (step 3) — models self-correct malformed args reliably when shown the error.
  • Truncate results deliberately (step 6): a 2MB JSON response is a context-window attack from your own database.

What breaks

  • Tool results are untrusted input: a scraped webpage or ticket body can carry prompt-injection that the model reads as instructions on step 7.
  • Non-idempotent handlers + retries = duplicate side-effects. Every mutating tool needs an idempotency key.
  • Timeouts that kill the handler but not the side-effect leave the world changed while the model believes the call failed.
FIG·06

MCP — the integration bus

The Model Context Protocol turns M×N custom integrations into M+N: one host runs one client per server over JSON-RPC, and every server exposes the same three primitives — tools, resources, prompts.

AGENT CORE

Design notes

  • The protocol is the contract: capability negotiation at initialize means hosts and servers evolve independently — the M×N integration matrix collapses to M+N.
  • Tools are model-controlled, resources are app-controlled, prompts are user-controlled. Choosing the right primitive is an API-design decision, not a naming one.
  • Server tool descriptions enter your context window (FIG·03). Twenty connected servers can spend your budget before the user types a word — lazy-load or search tools instead of front-loading all schemas.

What breaks

  • Trust boundary: a third-party MCP server injects text straight into your loop — tool descriptions and results are both injection surfaces. Treat servers like npm dependencies, not like config.
  • Remote servers add OAuth, network partitions, and version skew to what used to be a local function call. Timeouts and degraded modes are part of the design.
  • Two servers exporting similarly-named tools (search, query) make the model's tool choice ambiguous — namespace or curate.
FIG·07

The RAG pipeline, both lanes

Retrieval is two pipelines that must agree: an offline lane that turns documents into an index, and an online lane that turns a query into the handful of chunks worth spending context on.

AGENT CORE

Design notes

  • In agentic systems, retrieval is usually a tool the model calls with its own rewritten query — often several times with refinements — not a one-shot pre-step bolted before the prompt.
  • Hybrid beats pure-vector in practice: embeddings miss exact identifiers (error codes, SKUs, names) that BM25 catches trivially.
  • The reranker is the cheapest quality win in the stack: retrieve 50 loosely, keep the 5 a cross-encoder actually scores as relevant.

What breaks

  • Ingest/query drift: change the embedding model or chunking policy without re-indexing and retrieval quietly degrades — version the index like a schema.
  • Retrieval quality is invisible without its own eval: measure recall@k against a labeled set, or you'll debug "hallucinations" that are really retrieval misses.
  • Chunk boundaries that split tables, code blocks, or definitions hand the model half-facts it will confidently complete.
FIG·08

Memory architecture

"Memory" is three different stores plus a discipline: the volatile working context, persistent episodic/semantic/procedural stores, an async reflection process that writes back — and compaction keeping the window alive.

AGENT CORE

Design notes

  • Working context is not memory — it's a cache with brutal eviction. Anything worth keeping must be explicitly written somewhere persistent before compaction eats it.
  • Split by type because access patterns differ: episodic is append-only and searched rarely; semantic is small, hot, and loaded every session; procedural changes agent behavior and deserves review like code.
  • Reflection runs off the critical path — an agent that pauses mid-task to journal is spending the user's latency on its own bookkeeping.

What breaks

  • Memory poisoning: one wrong extracted "fact" gets recalled into every future session and compounds. Memories need provenance and an expiry/correction path.
  • Recall is retrieval (FIG·07) with the same failure modes — irrelevant memories in context are worse than none, they masquerade as ground truth.
  • Compaction summaries silently drop the detail that mattered ("port 5433, not 5432"). Summarize with a schema, not freeform prose.
PART III

Scale & Safety

FIG·09

Multi-agent orchestration

When one context window can't hold the job: an orchestrator decomposes work into typed tasks, isolated workers execute in parallel, and a critic gates what the synthesizer is allowed to merge.

SCALE

Design notes

  • Decompose by context, not by org chart. A subtask is worth a worker when it needs tokens the parent can't spare — not because "reviewer" sounds like a job title.
  • Task specs are the API: each worker gets a self-contained brief and returns structured results. If a worker needs to ask questions, the decomposition failed.
  • Fan-out multiplies cost linearly and error rate combinatorially — the critic exists because merging three unverified outputs compounds their mistakes.

What breaks

  • Telephone-game loss: every hop between agents drops detail. Pass artifacts (files, diffs, data) rather than summaries of summaries.
  • Two workers editing shared state concurrently — isolate write surfaces (per-worker worktrees) or serialize the writes.
  • Orchestrators that trust worker self-reports: "done ✓" from a worker is a claim, not a fact. Verification is the orchestrator's job.
FIG·10

Guardrails & the human-in-the-loop

Safety as a pipeline position, not a vibe: screen inputs, classify every proposed action by blast radius, auto-run only the reversible, gate the mutating on a human, and filter what leaves.

SAFETY

Design notes

  • Gate actions, not conversations. The reviewable unit is the proposed tool call with its exact arguments — a diff, a query, a recipient list — not a chat transcript.
  • Tier by reversibility: reads auto-run, reversible writes get logged, irreversible or outward-facing actions (send, delete, pay, deploy) get a human. Encode this in the policy engine, not in the prompt.
  • Ration the human's attention: if the gate fires on everything, approvals become rubber stamps within a week. Tight tiers keep review meaningful.

What breaks

  • Prompt-level guardrails alone: "never delete data" in the system prompt is a suggestion; the policy engine's deny is enforcement. Injected instructions can beat the former, not the latter.
  • Blocked actions returned as raw refusals cause retry loops — return a structured error the model can plan around.
  • The exfiltration triad: private data + untrusted input + an outbound channel in one agent. If you can't remove a leg, gate the outbound channel.
FIG·11

Failure modes → recovery, mapped

The five ways agent runs actually die, each paired with the mechanism that catches it. None of these are exotic — they're distributed-systems patterns pointed at a non-deterministic component.

RELIABILITY

Design notes

  • Row 3 is the dangerous one. Transport errors announce themselves; a plausible wrong answer doesn't. Budget most of your engineering into verification, not retries.
  • Recovery lives in the runtime, deterministically — asking the model to "please be careful" is not an error-handling strategy.
  • Checkpoint at step boundaries: a 40-step run that dies at step 39 should cost one step to finish, not forty.

What breaks

  • Retrying a mutating call that half-succeeded — hence idempotency keys before retry policies.
  • Compaction as a recovery can drop the very constraint that caused the failure, so the agent repeats it with a cleaner conscience.
  • Circuit breakers tuned by gut feel: derive thresholds from observed traces (FIG·14), or they'll fire on your best runs and sleep through your worst.
PART IV

Evals & Observability

FIG·12

The eval harness

The CI pipeline for a non-deterministic component: golden cases run N times through a sandboxed agent, three kinds of graders score the transcripts, and a regression gate decides what ships. This is the diagram most agent teams build last and need first.

EVALS

Design notes

  • Run every case N times. One trial of a non-deterministic system is an anecdote. Report pass@k (can it?) and pass^k (does it reliably?) — they answer different product questions.
  • Grade outcomes, not transcripts: assert on the final state of the sandbox — the ticket updated, the test passing, the file correct — not on whether the reasoning "looked right".
  • Start with 20 cases mined from real failures over 500 synthetic ones. Coverage of what actually goes wrong beats volume.

What breaks

  • Eval-set overfitting: prompts tuned against the same 50 cases for months are memorizing your test, not improving. Hold out a set that never influences iteration.
  • Unpinned dependencies: if the eval hits live APIs or a drifting model version, score changes don't mean what you think they mean.
  • A single aggregate score hides regressions — capability A improving 10% while capability B silently drops 15% reads as "+2% overall, ship it".
FIG·13

LLM-as-judge, calibrated

Using a model to grade a model works — but only as an instrument you've calibrated. The judge gets a rubric, bias controls, and a standing comparison against human labels. An uncalibrated judge is a random-number generator with confidence.

EVALS

Design notes

  • The rubric is the spec. Vague criteria ("is it helpful?") produce vibes; behavioral criteria with worked examples ("does it cite the retrieved source for every factual claim?") produce measurements.
  • Pairwise A/B is more reliable than absolute scoring for subtle quality gaps — models are better comparators than raters.
  • Report judge–human agreement (Cohen's κ) alongside every eval result. A judge you haven't measured against humans is itself an unevaluated model.

What breaks

  • Self-preference: judges from the same model family rate their sibling's style higher. Cross-family judging or ensembles blunt it.
  • Position and verbosity bias are large enough to flip pairwise conclusions — swap-and-rejudge isn't optional hygiene, it's the measurement.
  • Judge drift: upgrade the judge model and historical scores stop being comparable. Pin the judge per eval-set version, migrate deliberately.
FIG·14

The observability plane

An agent run is a distributed trace: every loop step is a span with token, cost, latency, and status attributes. One collector fans out to debugging, metrics, alerting — and the review queue that feeds your evals.

OBSERVABILITY

Design notes

  • Trace at the step level, always. Aggregate metrics tell you something regressed; only the span tree tells you it was turn 7, after that one tool timeout, in contexts over 80k tokens.
  • Cost is a first-class metric: $/task and tokens/task catch runaway loops days before the invoice does. Alert on rate-of-change, not absolutes.
  • Use the same trace format in the eval harness (FIG·12) and production — then a failed eval and a failed prod run are debuggable with the same tooling.

What breaks

  • Logging the metadata but not the payloads: latency without prompts and completions can't explain why quality moved. Record content, redact PII at the collector.
  • Sampling only errors: the "successful" runs users quietly abandoned are your biggest quality signal, and error-only sampling never sees them.
  • Traces with no session/user/version dimensions can't answer "did the new prompt help?" — tag every span with the config version that produced it.
FIG·15

The data flywheel

The whole atlas, closed into a loop: production produces traces, traces become eval cases, evals gate the next iteration, and the iteration ships back to production. Teams with this loop compound; teams without it guess.

EVALS

Design notes

  • The flywheel is the moat. Prompts get copied and models get upgraded, but a curated corpus of your domain's real failure cases — and the harness that runs them — compounds and doesn't transfer.
  • Model upgrades become cheap when the loop exists: swap the model, run the goldens, read the diff. Without it, every upgrade is a leap of faith.
  • Implicit signals (retries, abandons, escalations, edits to agent output) are higher-volume and more honest than thumbs — instrument them first.

What breaks

  • The loop silently opens: traces get sampled, nobody curates, the golden set fossilizes at last quarter's failure modes while the product moved on. Assign the curation rotation like on-call.
  • Curating only complaints skews the eval set toward loud users and rare disasters — sample the mundane middle too.
  • Personal data flowing from prod traces into eval sets without redaction turns your test fixtures into a compliance incident.
